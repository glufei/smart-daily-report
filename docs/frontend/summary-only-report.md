# 汇总版日报：内容边界与验证

当前代码版本为 v1.7.0（尚未发布 Release）。研究组日报只需要概括性工作量，不应在邮件、飞书群或网页中逐条披露提交标题、仓库链接、任务名称、消息正文、原始 ID 和逐条时间。本次变更沿用已有采集、成员映射和来源状态，不引入 AI 生成的工作结论。

| 位置 | 当前显示 | 数据边界 |
| --- | --- | --- |
| 网页历史与操作预览 | 报告日期、生成时间、来源状态；每位成员的三项数量、已获取记录合计、有记录类别和数量对比条 | React 不渲染逐条明细 |
| 邮件 HTML、飞书 Markdown | 同一日期的三项数量、已获取记录合计和有记录类别；邮件另有数量对比条 | 当前模板不输出逐条文字、链接和原始 ID |
| 本机 SQLite 与只读 API | 继续保留原始采集记录及时间 | **并未脱敏**；API 响应和浏览器网络工具仍可接触明细，只能供本机可信用户使用 |

成功来源无匹配记录时显示“0 条”；获取失败时数量未知，不计入合计。合计是已获取的三类记录条数之和，有记录类别是成功来源中数量大于零的类别数；它们和数量对比条都不代表工作量或成果质量。计数来自已经采集、筛选并映射到成员的结构化记录，不对工作质量、进度或涉密内容作推断。未启用来源在操作预览中标为“未启用”并排除在合计外；旧的只读历史结构只保存 success/failure 状态，不应根据零条推断来源是否启用。若要进一步限制本机 API 读取原始记录，需要单独修改 API 契约及存储/访问边界；本次按用户选择保留它们。

## 升级已保存的日报

历史 Markdown/HTML 是当时的快照，不随代码升级自动改写。当前网页从历史结构化记录计算汇总，因此看起来已是新布局，但旧邮件或飞书正文仍可能包含明细。操作模式会在接受推送前比较快照与当前汇总模板；不匹配时返回 `409 report_requires_regeneration`，不会发送。使用当前代码重启前后端，对需要发送的日期重新「采集并生成」，核对预览，再独立确认邮件/飞书渠道。重新生成会覆盖该日期的本机日报快照，既有已发邮件和群消息无法撤回；不要为了验证而发送真实通知。CLI 正常运行会重新生成当日内容后再按配置推送，使用前同样应核对日期和目标。

旧规范中 v1.4/v1.5 的“汇总＋明细”、来源分组和逐条时间展示是历史阶段的验收事实，现由本汇总版规则取代。源码及接口字段仍保留原始记录，是用户明确选择的本机留存边界。

本次没有用真实 GitHub、飞书或 SMTP 执行采集和推送，也没有对既有私有日报做迁移；真实投递内容需在用户选定日期重新生成并预览后由用户确认。
