## 1. 背景与目标

### 1.1 背景

团队成员每天需要从代码提交、任务进展和协作沟通中整理工作信息并手动撰写日报。手工整理耗时，容易遗漏，且格式不一致；团队负责人也难以快速掌握成员工作动态。

### 1.2 目标

构建一个可由定时任务触发的工具，从 GitHub 与飞书采集团队当日工作记录，按成员聚合，生成结构化日报，并通过邮件及飞书群机器人推送。日报固定包含三个业务板块：代码提交、任务进展、协作沟通。

### 1.3 用户与运行方式

- 目标用户：团队成员、团队负责人及负责部署该工具的维护者。
- 初期规模：5 名团队成员；配置应允许增加成员，但本期性能验收以 5 人为基准。
- 运行方式：工作日由外部定时任务触发生成 CLI；该流程不常驻。v1.1 新增按需启动的本机 Web 查看入口及只读 API，供浏览器查看既有日报。

## 2. 范围

### 2.1 本期要做

1. 从配置的 GitHub 仓库采集指定日期范围内的提交记录。
2. 从配置的飞书项目/任务来源采集当日有状态变更的任务记录。
3. 从配置的飞书群采集与工作相关且通过关键词规则筛选的消息记录。
4. 依据 GitHub 账号与飞书账号映射，将三类数据按成员归属并生成三段式日报。
5. 输出可读的 Markdown 与 HTML；Markdown 用于飞书机器人，HTML 用于 SMTP 邮件。
6. 在工作日生成日报；周末及配置的法定节假日不生成、不推送日报。
7. 任一数据源失败时继续处理其他数据源，并在日报对应板块明确标记“数据获取失败”；无记录时显示“今日无记录”。
8. 提供 `--check` 健康检查模式，用于验证配置和外部连接并返回可供脚本判断的退出状态。
9. 将日报历史保存至本地 SQLite。
10. **v1.1 新增**：提供中文只读 Web 页面，允许选择日期，查询本地 SQLite 中已经保存的团队日报，展示团队名、报告日期、生成时间、全部成员及代码提交/任务进展/协作沟通三个板块。
11. **v1.1 新增**：页面分别展示加载中、有日报、该日期尚无日报、请求失败；日报内区分“今日无记录”和“数据获取失败”，不得将请求错误转换为空日报。
12. **v1.1 新增**：通过确认后的 OpenDesign 软件 UI 完成页面原型及至少一次有记录的设计迭代，留存工具版本/来源、UI 操作证据、输入、输出和修改依据，再实现可维护的前端代码。设计阶段仅使用虚构数据。
13. **v1.1 新增**：新增前后端分离的只读 HTTP 查询接口；查询不触发采集、生成、持久化或推送。页面与 API 默认仅在本机访问。

### 2.2 本期不做

- 不生成 AI 自然语言摘要或改写内容；日报仅对源数据进行筛选、归类和格式化。
- 不提供手动生成、编辑、删除或重新推送日报的 Web 能力；生成和推送仍由既有 CLI/外部定时任务触发。
- 不提供跨日期列表、全文搜索、统计图表、成员/配置管理后台。
- 不提供公网/局域网部署、多用户登录、角色权限或远程数据库；v1.1 只读 Web/API 为本机按需启动。
- 不采集考勤、工时、日历、文档编辑等未列明的数据源。
- 不自动创建或修改 GitHub/飞书中的任务、评论或消息。
- 不将 SQLite 历史同步到远程数据库或云存储。

## 3. 日报逻辑

每位成员一段，按以下固定顺序组织；团队日报包含全部成员，即使某成员没有记录也保留该成员区段。

1. **代码提交**：展示当日提交记录（仓库、提交摘要、时间及链接等契约字段）。
2. **任务进展**：展示当日状态变更的任务及当前状态。
3. **协作沟通**：展示符合关键词过滤规则的消息摘要字段/原文片段；不得展示命中敏感词规则的消息。

每个板块的状态分别为：有记录、正常采集但无记录、采集失败。失败状态不可伪装为空数据。若所有配置数据源均失败，则不生成或推送空日报；部分数据源成功时继续生成并显示失败标识。

## 4. 成功标准与验收

- [ ] 5 人团队单次完整生成耗时小于 60 秒；耗时范围从流程启动至日报内容生成完成，不含外部邮件/飞书服务商的投递确认时间。
- [ ] 日报按成员分组，且每位成员依次包含代码提交、任务进展、协作沟通三个板块。
- [ ] Markdown 与 HTML 均可从同一份结构化日报数据生成，内容和状态一致。
- [ ] 一个数据源失败时，其他数据源仍完成采集；日报对应板块标注“数据获取失败”。
- [ ] 数据源正常且无记录时显示“今日无记录”。
- [ ] 所有数据源失败时不生成/推送空日报，进程以失败状态结束并写出结构化错误日志。
- [ ] 周末及配置的法定节假日执行时跳过生成和推送，并记录跳过原因。
- [ ] `--check` 对有效配置及可达依赖返回成功状态；配置缺失或必需依赖不可用时返回失败状态并给出可诊断结果。
- [ ] GitHub 与飞书身份映射缺失或冲突时有确定的处理结果并写出诊断，不得静默合并为错误成员。
- [ ] 敏感消息内容不会进入日报、正常日志或历史日报。

### 4.1 v1.1 前端验收（实现进度见 tasks.md）

- [x] **F01 — OpenDesign 使用证据**：记录确认后的软件仓库/版本或提交、许可证、UI 操作证据、设计输入、初版与迭代版产物，以及至少一项用户可见修改的前后对照；不能以普通手写原型或仅 CLI 生成冒充软件 UI 迭代。
- [x] **F02 — 日报查询与一致性**：为 SQLite 写入已知日期的 fixture 后，选择该日期，页面显示与存储相同的团队、日期、生成时间、成员顺序和三板块记录；无记录成员仍显示，来源失败板块显示“数据获取失败”。
- [x] **F03 — 状态可区分**：自动化验证成功零记录、单来源失败、日期不存在（404）、日期非法（400）、存储错误（500）和网络不可达；页面以不同文案区分无日报、板块无记录、来源失败和查询失败。切换日期时旧请求不得覆盖新日期结果。
- [x] **F04 — 查询只读**：查询前后日报行数和内容一致，缺失数据库不被创建；测试断言查询不调用 Collector、Generator、Notifier 或写入方法。查询其他日期或刷新页面也不得发送通知。
- [x] **F05 — 安全展示**：API 仅返回契约允许字段；凭证、Webhook、配置、数据库路径、堆栈及已被过滤的敏感消息不进入响应、页面或正常日志。外部文本作为文本展示；非 HTTP(S) 链接不可点击，恶意 HTML fixture 不执行。
- [x] **F06 — 页面可用与构建**：在 375×812 和 1440×900 视口下无页面级横向溢出；日期选择、查询与错误后的重新查询可通过键盘操作且具有可访问名称；类型检查、前端构建和相关自动化测试全部通过。
- [x] **F07 — 后端回归**：既有 CLI 成功/降级/全源失败/非工作日/推送部分失败语义保持，全部 Python 测试通过且业务代码覆盖率不低于 90%；仅安装 CLI 基础依赖也能导入并运行 CLI。

## 5. 异常与边界

- **限流与重试**：对可重试网络错误、超时、HTTP 429 及 GitHub 限流响应执行有上限的确定性重试；优先遵守 `Retry-After` / reset 时间。重试耗尽后将该数据源结果标记为失败，不阻塞其他来源。非重试状态码不重试。
- **飞书 Token**：收到明确的 Token 过期/无效响应时刷新一次并重放原请求一次；刷新失败或再次鉴权失败则将对应来源标记为失败。
- **非工作日**：周末默认跳过；法定节假日由配置日历显式提供，未配置的节假日数据不作推断。
- **空结果**：有效采集返回空列表表示无记录；不得与采集错误混用。
- **身份映射**：映射表按规范化后的外部账号唯一匹配。未映射数据归入“未映射成员”诊断区，不与其他成员混淆；是否在日报显示须由配置明确决定，默认不显示源内容，只记录计数和告警。
- **敏感词**：敏感词命中即排除整条消息；命中词及原文不得被写入日志或 SQLite 日报内容。过滤规则由配置提供并有测试覆盖。
- **推送部分失败**：一种推送渠道失败不阻止另一渠道；分别记录结果。推送失败不删除已生成日报历史。
- **配置/密钥缺失**：启动时校验必填配置；秘密通过环境变量或安全运行环境注入，不在样例配置、日志和仓库中写入真实凭证。

## 6. 术语

| 术语 | 定义 |
|---|---|
| 日报 | 指定工作日团队成员工作记录的结构化汇总 |
| 数据源失败 | 请求或解析未能产生可信结果；与成功返回零条记录不同 |
| 非工作日 | 周末或配置日历中标记的法定节假日 |
| 成员映射 | 将 GitHub 账号、飞书账号映射到同一内部成员标识的配置 |
| 敏感词过滤 | 在内容被持久化或输出前排除命中规则的消息 |

## 7. 规范边界

本文件定义目标、范围和可观察的验收结果。模块划分、数据字段、函数签名、重试策略细节及 ADR 由 `design.md` 和 `specs/contracts/` 定义；任务交付物及任务级验收由 `tasks.md` 定义。

v1.0 中“无 Web 界面/常驻 API”的边界由本规范 §2 明确修订为“本机、只读、按需启动”；选取这一条新边界是为了满足导师的前端迭代要求。用户已确认 v1.1，以此为准，不得同时沿用旧禁令；旧版本仅作为 Git 历史保留。
