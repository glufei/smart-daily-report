## 1. 背景与目标

### 1.1 背景

团队成员每天需要从代码提交、任务进展和协作沟通中整理工作信息并手动撰写日报。手工整理耗时，容易遗漏，且格式不一致；团队负责人也难以快速掌握成员工作动态。

### 1.2 目标

构建一个可由定时任务触发的工具，从 GitHub 与飞书采集团队当日工作记录，按成员聚合，生成结构化日报，并通过邮件及飞书群机器人推送。日报固定包含三个业务板块：代码提交、任务进展、协作沟通。

### 1.3 用户与运行方式

- 目标用户：团队成员、团队负责人及负责部署该工具的维护者。
- 初期规模：5 名团队成员；配置应允许增加成员，但本期性能验收以 5 人为基准。
- 运行方式：外部定时任务可按任意日历日期触发生成 CLI；该流程不常驻。v1.1 提供本机历史查看；v1.2 增加显式启用的本机操作模式，浏览器可触发采集生成，预览后独立触发推送。原只读启动方式继续可用。

## 2. 范围

### 2.1 本期要做

1. 从配置的 GitHub 仓库采集指定日期范围内的提交记录。
2. 从服务器配置的已授权飞书任务清单读取任务，按配置时区展示所选日期完成的任务；仅标题更新不计入完成记录，不声称复原任意历史状态变更。
3. 从配置的飞书群采集与工作相关且通过关键词规则筛选的消息记录。
4. 依据 GitHub 账号与飞书账号映射，将三类数据按成员归属并生成三段式日报。
5. 输出可读的 Markdown 与 HTML；Markdown 用于飞书机器人，HTML 用于 SMTP 邮件。
6. 对任意有效日期生成日报；周末及配置中列出的法定节假日也可生成、预览和推送，不因日期类型拦截。
7. 任一数据源失败时继续处理其他数据源，并在日报对应板块明确标记“数据获取失败”；无记录时显示“今日无记录”。
8. 提供 `--check` 健康检查模式，用于验证配置和外部连接并返回可供脚本判断的退出状态。
9. 将日报历史保存至本地 SQLite。
10. **v1.1 新增**：提供中文只读 Web 页面，允许选择日期，查询本地 SQLite 中已经保存的团队日报，展示团队名、报告日期、生成时间、全部成员及代码提交/任务进展/协作沟通三个板块。
11. **v1.1 新增**：页面分别展示加载中、有日报、该日期尚无日报、请求失败；日报内区分“今日无记录”和“数据获取失败”，不得将请求错误转换为空日报。
12. **v1.1 新增**：通过确认后的 OpenDesign 软件 UI 完成页面原型及至少一次有记录的设计迭代，留存工具版本/来源、UI 操作证据、输入、输出和修改依据，再实现可维护的前端代码。设计阶段仅使用虚构数据。
13. **v1.1 新增**：新增前后端分离的只读 HTTP 查询接口；查询不触发采集、生成、持久化或推送。页面与 API 默认仅在本机访问。
14. **v1.2 新增 — 真实 FastAPI 对接**：页面向本项目 FastAPI 提交生成/推送操作并查询执行结果；产品运行不启动 fixture 服务、不硬编码日报、不在接口失败时回退 Mock。历史 GET 保持只读。
15. **v1.2 新增 — 真实 GitHub/飞书采集**：点击“采集并生成”后，后端按服务器配置与日期调用真实 GitHub 提交、飞书任务和群消息 API，复用映射/过滤/生成/SQLite 能力；不发送任何通知。页面区分已启用来源成功、失败和未启用，不把未启用来源计为真实采集成功。
16. **v1.2 新增 — 真实推送**：预览已保存的具体日报版本，显示配置中的目标摘要，选择邮件/飞书渠道并点击确认后，由后端调用 SMTP/飞书机器人。推送不重新采集、不重新生成，不能发送已被另一轮生成替换的未确认版本。
17. **v1.2 新增 — 可确认的结果**：分别展示生成、来源和渠道结果；服务商接受通知与收件人实际收到是不同证据。重复点击、重复请求、断线及进程重启不能被当作安全的自动重发依据；结果不确定时显示“结果待核实”。

### 2.2 本期不做

- 不生成 AI 自然语言摘要或改写内容；成员工作总结仅按结构化记录数量和来源状态确定性生成，不推断源数据未表达的工作结论。
- 不提供编辑、删除日报或任意重发已接受/结果不确定通知的 Web 能力。手动生成与首次推送纳入 v1.2；明确失败且尚未接受的渠道可由用户单独再次提交，不能连带重发成功渠道。
- 不提供跨日期列表、全文搜索、统计图表、成员/配置管理后台。
- 不提供公网/局域网部署、多用户登录、角色权限、浏览器保存上游凭证或远程数据库；本轮操作令牌仅用于本机单维护者操作，不扩展为账号系统。
- 不采集考勤、工时、日历、文档编辑等未列明的数据源。
- v1.2 不复原飞书任务的任意历史状态迁移，也不展示已重新打开任务的历史完成事件；仅依据当前可读任务的完成时间筛选。
- 不通过采集接口创建或修改 GitHub/飞书中的任务、评论或源消息；仅在用户显式推送时发送本规范允许的日报通知。
- 不将 SQLite 历史同步到远程数据库或云存储。

## 3. 日报逻辑

每位成员一段，按以下固定顺序组织；团队日报包含全部成员，即使某成员没有记录也保留该成员区段。

1. **今日总结**：列出当前成员代码提交数、当日完成任务数、合规协作消息数；每个来源分别遵循该成员/来源的成功、无记录、失败状态。失败来源显示“获取失败，数量未知”，不得写成 0；成功且无记录显示“0 条”。总结只做计数，不生成或改写自然语言结论。
2. **代码提交**：展示当日提交记录（仓库、提交摘要、时间及链接等契约字段）。
3. **任务进展**：展示已授权清单中所选日期完成的任务及完成时间；多个负责人分别映射至对应成员，不编造变更前状态。
4. **协作沟通**：展示符合关键词过滤规则的消息摘要字段/原文片段；不得展示命中敏感词规则的消息。

每个板块的状态分别为：有记录、正常采集但无记录、采集失败。失败状态不可伪装为空数据。若所有配置数据源均失败，则不生成或推送空日报；部分数据源成功时继续生成并显示失败标识。

## 4. 成功标准与验收

下列十项保留原始目标清单的记号；当前实现进度以 `tasks.md`、F01–F07、R01–R12 和验收记录为准，不把这些未勾选记号解释为十个模块尚未开发。现有 5 人离线计时测试只覆盖日报生成器，不含外部采集及完整管道；真实运行耗时仅覆盖已有样本，因此“5 人完整流程小于 60 秒”尚未得到端到端负载验证。最终交付范围见 `docs/frontend/v1.2-final-handover.md`。

- [ ] 5 人团队单次完整生成耗时小于 60 秒；耗时范围从流程启动至日报内容生成完成，不含外部邮件/飞书服务商的投递确认时间。
- [ ] 日报按成员分组，且每位成员依次包含代码提交、任务进展、协作沟通三个板块。
- [ ] Markdown 与 HTML 均可从同一份结构化日报数据生成，内容和状态一致。
- [ ] 一个数据源失败时，其他数据源仍完成采集；日报对应板块标注“数据获取失败”。
- [ ] 数据源正常且无记录时显示“今日无记录”。
- [ ] 所有数据源失败时不生成/推送空日报，进程以失败状态结束并写出结构化错误日志。
- [x] 对任意 `YYYY-MM-DD` 有效日期完成生成、预览及配置渠道推送；周末或 `team.holidays` 中的日期均不得触发日期拦截（CLI/Web 集成测试通过；真实外部收件未在本轮执行）。
- [ ] `--check` 对有效配置及可达依赖返回成功状态；配置缺失或必需依赖不可用时返回失败状态并给出可诊断结果。飞书任务和消息检查要求 HTTP 成功且响应为字典、业务码为整数 0；缺失码、布尔值、浮点值或字符串不能证明依赖可用。轻量检查不代替完整采集或实际收件验收。
- [ ] GitHub 与飞书身份映射缺失或冲突时有确定的处理结果并写出诊断，不得静默合并为错误成员。
- [ ] 敏感消息内容不会进入日报、正常日志或历史日报。

### 4.2 v1.2 验收（2026-10-05全部通过）

当前证据见 [验收记录](../docs/frontend/v1.2-acceptance.md) 和 [完成情况审查](../docs/frontend/v1.2-completion-audit.md)。勾选代表下列明确范围通过；真实三类非空来源分别按实际日期核对，最终回归和可复现交付文档均通过。

- [x] **R01 — 真实运行入口**：产品前端通过真实 FastAPI 操作与历史接口工作；默认启动不导入或运行 fixture，接口失败不显示预制成功数据。
- [x] **R02 — 生成不发送**：用户选定任意有效日期并点击生成后，GitHub/飞书按已启用配置采集，日报保存且页面内容与 GET 一致；SMTP 与机器人发送次数为零。仅查看、刷新和操作状态 GET 也不触发采集/发送。
- [x] **R03 — 来源与日期可信**：真实 GitHub 提交、已授权飞书清单中所选日期完成的至少一条任务及通过关键词/敏感词规则的群消息，分别有可映射记录在页面展示并与源平台核对。任务按完成时间和配置时区筛选，仅标题更新、未完成及日期外任务不计入；正常零条、失败、未启用可区分。所有已启用来源失败或未启用任何来源时不生成、不覆盖已有日报。
- [x] **R04 — 凭证边界**：操作模式缺少本机操作令牌或有效配置时启动失败；受保护接口缺失/错误令牌返回 401，未允许 Origin 返回 403，均无副作用。上游凭证仅在后端使用；浏览器只传本项目操作令牌，不进入 URL、持久浏览器存储、构建产物、响应或日志。

## 5. 异常与边界

- **限流与重试**：对可重试网络错误、超时、HTTP 429 及 GitHub 限流响应执行有上限的确定性重试；优先遵守 `Retry-After` / reset 时间。重试耗尽后将该数据源结果标记为失败，不阻塞其他来源。非重试状态码不重试。
- **飞书 Token**：收到明确的 Token 过期/无效响应时刷新一次并重放原请求一次；刷新失败或再次鉴权失败则将对应来源标记为失败。
- **日期规则**：生成和推送接受任意格式有效的日期；周末及配置中的节假日不构成拦截。配置中的 `team.holidays` 为兼容保留项，不参与生成或推送决策。
- **空结果**：有效采集返回空列表表示无记录；不得与采集错误混用。
- **身份映射**：映射表按规范化后的外部账号唯一匹配。未映射数据归入“未映射成员”诊断区，不与其他成员混淆；是否在日报显示须由配置明确决定，默认不显示源内容，只记录计数和告警。
- **敏感词**：敏感词命中即排除整条消息；命中词及原文不得被写入日志或 SQLite 日报内容。过滤规则由配置提供并有测试覆盖。
- **推送部分失败**：一种推送渠道失败不阻止另一渠道；分别记录结果。推送失败不删除已生成日报历史。
- **配置/密钥缺失**：启动时校验必填配置；秘密通过环境变量或安全运行环境注入，不在样例配置、日志和仓库中写入真实凭证。

## 6. 术语

| 术语 | 定义 |
|---|---|
| 日报 | 指定日期（含周末与配置节假日）的团队成员工作记录结构化汇总 |
| 数据源失败 | 请求或解析未能产生可信结果；与成功返回零条记录不同 |
| 日历日期 | 通过 `YYYY-MM-DD` 校验的任意日期，包括周末及配置节假日 |
| 成员映射 | 将 GitHub 账号、飞书账号映射到同一内部成员标识的配置 |
| 敏感词过滤 | 在内容被持久化或输出前排除命中规则的消息 |

## 8. 下一轮需求变更：操作反馈与可选邮件收件人（2026-10-11，规范已确认）

### 8.1 用户目的、确认范围与规则变更

用户希望维护者点击“查询执行结果”和“预览日报”后能明确知道请求是否正在处理、是否成功及结果在哪里；发送邮件时能只选择自己的邮箱、导师邮箱或两者。用户已确认仅从后端配置邮箱中勾选，不在页面临时输入地址。

用户明确不新增按收件人防重复发送功能，并进一步确认：允许重新选择收件人、独立确认后再次发送同一版本邮件；保留同一次请求去重、断线后不自动重发以及飞书现有防重复规则。这修订了 §2.2、R07 中对邮件整渠道禁止主动再次发送的限制。用户随后以“开始工作”确认书面规范；实施计划随后获确认，Task19–20已完成。此前 v1.2 的已验收规则是历史基线；新规则在计划审查、TDD 实现及验收之后生效，本分支已按新规则实现，原v1.2.0标签保持历史基线。

### 8.2 功能范围

1. 查询按钮就近显示“正在查询执行结果”，完成后显示本次查询时间、操作类型、所属日期及执行状态；即使服务器结果未变化也有本次查询完成反馈。没有操作记录明确提示“暂无执行记录”，与认证成功、查询失败分开。
2. 预览按钮就近显示“正在加载日报预览”；成功时显示所选日期和完成反馈，并将视口与键盘焦点定位到日报正文标题。无日报、网络失败及鉴权失败明确提示，失败和日期切换不能继续使用旧的操作预览或旧确认框。
3. 认证后的预览列出后端配置的邮箱，默认均不勾选。选邮件渠道时至少勾选一个地址才能提交；允许仅选飞书。确认框展示日期、版本、实际收件地址及所选飞书目标，取消不发送。
4. 邮件仅发送给本次确认的配置子集；客户端篡改加入配置外邮箱时后端拒绝。接口缺少邮件目标时不得回退为向所有配置邮箱发送。
5. 邮件再次发送须由用户发起新请求并独立确认；同键同内容返回原结果，同键不同内容为冲突。页面提示“再次推送可能产生重复邮件”；已受理与未知状态仍如实显示，不自动重复 POST。
6. 查询与预览保持只读；生成继续不发送，推送继续使用确认过的日报快照。日期规则不限制周末或配置节假日；来源采集、飞书目标及默认只读运行方式保持。
7. React 每位成员先展示“今日总结”，其计数必须由当前日报 DTO 中的成员记录数组及来源状态推导：成功且无记录为 `0 条`，失败为 `获取失败，数量未知`，未启用或仍在采集时使用独立状态文案。页面不得将失败误报为零，不增加 API 请求。

本轮不新增收件人管理后台、逐收件人发送结果账本或新的反重复规则。邮件仍以一次 SMTP 提交处理所选列表，保留邮件渠道的全部受理、部分受理、拒绝、未知结果。
